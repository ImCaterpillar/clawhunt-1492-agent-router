# 实现说明 — #1492 Agent 协作路由

## 需求还原

企业知识库与多 Agent 协作系统（系列 50 单）的拆单之一。本单范围：
**按角色与任务类型路由，明确失败回退和人工接管入口**。

验收标准：**至少演示正常路由、无匹配和转人工三类路径**——即路由层
必须有清晰可观测的三条路径，且人工接管是真入口而非摆设。

## 设计

### 1. 路由表模型

```
规则 = {role?, task_type?, target | human=True, priority, note, rule_id}
匹配条件 role/task_type 支持：
  - str:     精确相等
  - list:    值在列表中（如 support 的两种任务类型）
  - "any"/"*": 通配（始终匹配）
  - None:    该字段不参与匹配
```

### 2. 三条路径

| 路径 | 触发条件 | 结果 |
|---|---|---|
| **正常路由** | 命中 target 规则 | `{path: "route", target: "xxx-bot", rule_id}` |
| **无匹配** | 没有任何规则命中 | `{path: "no_match"}` + 原因；配了 default_target 则降级转发 |
| **转人工** | 命中 human=True 规则 | `{path: "human", human_ticket: "HUMAN-XXX"}`，进人工队列 |

关键设计决策：
- **转人工优先于转发**：先扫人工规则再扫转发规则——高危操作（资金、
  权限）绝不能被自动 agent 拦截，这是人工接管的硬保证。
- **无匹配不静默丢弃**：业务上"无匹配"是合法输入（新任务类型上线
  初期），必须显式可观测——要么降级 default_target，要么返回明确的
  no_match + 原因。静默丢弃会让任务消失，是路由层最危险的失败模式。
- **兜底规则 priority 最低**：`{role: "any", task_type: "unknown_operation",
  target: "fallback-bot", priority: 1}` 明确吃掉剩余情况，配合不配
  default_target 的 no_match 路径，两条回退机制并存互补。

### 3. 人工接管入口

```
route() 命中 human 规则 -> human_queue.append({ticket: "HUMAN-XXX",
                                               task, status: "awaiting_human"})
claim_human(ticket, handler)   # 人工认领 -> status=claimed
pending_human()               # 待认领清单
```

人工接管是**真实入口**：能认领、能查待办、认领后从待办消失（测试 8/9）。

### 4. 审计与统计

每次路由写入 `delivery_log`（含 path/target/rule_id/task/ts），
`stats()` 汇总三路径计数——测试 11 断言枚举精确等于
`{route, no_match, human}`，证明不存在第四条隐藏路径。

## 与系列其他单的关系

- 02 角色卡（#1489）：定义 bot 的身份与职责边界；
- 03 会话隔离（#1490）：隔离层保证跨 bot 读不到记录；
- **05 协作路由（本单）**：决定"任务去哪"。路由是转交，不改变隔离
  边界——转交后目标 bot 仍只读自己的命名空间；转人工的任务则带上
  HUMAN-XXX 单，由人接管，不会进任何 bot 的隔离会话。
